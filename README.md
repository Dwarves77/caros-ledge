# Caro's Ledge

Freight sustainability intelligence. This tree is the clean-room rebuild: a new repository, no history from the old one. It is building; `src/app/page.tsx` says so.

The plan is in `docs/BUILD-PLAN-2026-10-12.md`; how it is executed is in `docs/PART2-AGENT-PLAN-2026-10-15.md`. docs/WHY-2026-10-16.md is the operator's rationale: read it before any build or improvement decision; its section 7 is the decision procedure.

## Rules

1. Every feature of the old product is kept; each is written once, as the best version of itself.
2. Everything is free: no metered model API, no Browserless.
3. Hierarchy: `src/core` (substrate, at most 25,000 code lines), `src/features/<name>`, `src/ui`, `src/app` (thin routes). `src` at most 75,000 (raised from 60,000 by the operator on 2026-10-16 after wave 2 landed every feature at 100 to 163 percent of the plan budgets).
4. Every file under `src/` carries `// Ported from old_repo/<path> (lines a-b[, c-d])`, or is listed with a reason in its slice's allow-file `scripts/ci/new-files/<slice>.txt` (lines of `path | reason`). `tree-checks` validates every range against `scripts/ci/old-tree-lines.json` (line counts of every file under `fsi-app/` at old repo commit 646fb098c, `fsi-app/` prefix dropped, regenerated by `scripts/gen/old-tree-lines.mjs`). **Count lines the way `wc -l` does** (newline-terminated lines): a range ends at most at that count, and an unknown path fails. The check runs over the working tree, so an untracked file is checked locally exactly as on the PR.
   Merger note: if a merge brings a line into a retired `scripts/ci/new-files.txt`, move it into your slice's file under `scripts/ci/new-files/` and delete the old one. Route guards in `tests/core/structure.test.ts` are read from the tree; add no per-slice literal there.
5. A dependency needs a line in the `budget` block of `package.json`. No `@anthropic-ai/*`, `openai`, or Browserless.
6. The database is `supabase/schema.sql` plus forward files in `supabase/migrations/`, each ending in a DO-block self-check.
7. Facts live in the database; code and docs cite them and never restate them.
8. One workflow, `.github/workflows/ci.yml`. A red run is fixed at the root cause before any re-trigger.
9. Lint has zero warnings: no unused variables, no `any`, ordered imports, no console outside `src/core/shared/log.ts`.
10. No personal name, email or home path anywhere in the tree.

## Proofs (all in CI)

- `ci`: `npm run lint`, `typecheck`, `build`, `test`, `tree-checks`, `loc`.
- The `ci` job's last step posts or updates ONE PR comment (marker `<!-- ci-report -->`) with the run id, every job's conclusion and the loc table. Read it there; do not edit the PR body for it.
- `schema`: an empty Postgres 15 is built into the Supabase project the migrations are written for, from `scripts/ci/data/production-shape.json` (roles and their settings, memberships, schema and default ACLs, server settings, the database owner, as production reports them; `public.live_check_production_shape()` asks the same question of production, and the `production-shape` live check diffs the two). `supabase/schema.sql` and every migration then apply as the production-shaped `postgres` role (`npm run schema:apply`): each migration prints its own `<id> OK`, changes exactly the catalog classes its header declares, and its `down/NNNN.sql` (or its `-- irreversible:` recovery) is applied and catalog-compared. Then `scripts/ci/properties.mjs` runs every check of `scripts/ci/checks/` over every schema the app reads: a check fails on any offender no waiver names (`scripts/ci/baseline-waivers.json` names each waived row, its reason and the slice that owes the fix, and a waived row that is gone must be deleted), and each check is attacked by the planted violation in `scripts/ci/fixtures/<key>.sql`, whose `-- expect:` lines say what each branch of the check returns. The MemDb every test runs over is compared with this database (`scripts/ci/checks/memdb-conformance.mjs`).

Edits to `supabase/schema.sql` against the production dump are recorded in `supabase/SCHEMA-NOTES.md`. Environment variable names are in `.env.example`.

## Parity capture secrets

The `parity` job (`tests/parity/capture.mjs`) reads six repository secrets. A route whose account has no credentials is recorded `skipped` ("no <account> credentials"), never failed.

| Secret | Used for |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | The built app's Supabase project (placeholders when unset) |
| `LIVE_SMOKE_EMAIL`, `LIVE_SMOKE_PASSWORD` | `auth: "member"` routes: every signed-in route except `admin` |
| `LIVE_ADMIN_EMAIL`, `LIVE_ADMIN_PASSWORD` | `auth: "admin"` routes: `/admin` (a platform admin account); read only when `PARITY_ADMIN=1` (the deployed-preview capture). In the CI job admin routes are recorded `skipped`: "admin routes gate on the deployed preview" |

## Schema checks on a workstation

`npm run schema:local` starts a throwaway PostgreSQL 15 (the `embedded-postgres` devDependency, a temp data dir, a free port), runs `scripts/ci/schema-apply.mjs` against it (schema.sql, every migration, the property checks, the catalog diff) and deletes the instance on every exit path. There is no psql in the path: the CI scripts run their SQL through the `pg` client (`scripts/ci/psql.mjs`), so CI and a workstation run the same code.

## The push gate

`npm run gates` (`scripts/ci/gates.mjs`) is the one list of checks: workflow validity, lint, typecheck, build, tests, tree checks, UI checks, LOC, connections, columns, propagation method versions, migration checks, fail-fast, in CI's order. The `ci` job runs this same script, so CI and the hook cannot drift. When a file under `supabase/` differs from the upstream branch (`origin/main` if none), it also runs `schema:local`.

`.githooks/pre-push` runs it before every push and refuses the push on a failure; it also refuses a head commit carrying `[skip ci]` (a PR never ends on an unproven SHA). `npm ci` installs the hook (`prepare` sets `core.hooksPath` to `.githooks`), and tree-checks fails if the prepare script or the executable hook is missing. The hook is the gate: bypassing it (`--no-verify`, unsetting `core.hooksPath`) is a rule violation, never a step.
